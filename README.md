## Local setup

From `D:\Tech Website`:

```powershell
npm ci
node scripts/generate-assets.mjs
npm run db:migrate
# Local-only configuration: generates a private bootstrap secret, no production changes.
node scripts/prepare-local-tests.mjs
npm run build:web
npx wrangler dev --local --port 8787
```

Open localhost port 8787. `.dev.vars` and `.test-bootstrap-secret` are ignored by Git. Never deploy local test mode. The production configuration guard rejects an absent/unconfigured production environment.


`npm run test:e2e` automatically creates a fresh isolated local D1 persistence directory, temporarily generates local-only test secrets and restores existing local configuration afterward. The suite uses a real Worker and migrated D1, not mocked persistence. The API test bootstraps a random test-only administrator and closes bootstrap. Do not run raw bootstrap tests against an existing administrator database or production. Credentials generated by tests are not a public/default login. On Windows, an installed Chrome can be selected with `$env:PLAYWRIGHT_CHANNEL='chrome'` when the Playwright browser download is unavailable. Run E2E commands sequentially to avoid runtime and report-directory collisions.

## Secure initial administrator

Set a long random `ADMIN_BOOTSTRAP_SECRET` in `.dev.vars` for local operation. With the Worker running, send same-origin JSON to `POST /api/admin/bootstrap`, including `Origin: http://localhost:8787` and `X-Bootstrap-Secret`. Supply your own email and a password of at least 14 characters containing upper/lower case, a number and symbol. Bootstrap closes atomically after the first administrator. Remove the bootstrap secret afterward. Production secret configuration requires owner approval.

Sign in at `/admin`. Sessions last eight hours, are hashed in D1, and use HTTP-only SameSite cookies (Secure on non-local hosts). Admin mutations require the issued CSRF token. New password hashes use versioned standard PBKDF2-HMAC-SHA256 through `@noble/hashes`; see `docs/SECURITY.md` for limitations and review requirements.

## Configuration and integrations

For the Git-connected Cloudflare Pages build and the missing-homepage fix,
see `docs/PAGES_DEPLOYMENT.md`. `npm run build:web` now includes a Pages
advanced-mode Worker, not only frontend assets. Database and provider setup
are still required for forms and administrator access.

Use `.env.example` as the server configuration reference. Production requires a real D1 database ID, HTTPS public URL, Cloudflare account authorization, Turnstile site/secret keys, and optionally a Resend API key and verified sender. No actual keys are supplied. Forms fail closed when production security verification is unavailable. Successful persistence never claims that an email was delivered.

Notification records are placed in `email_outbox`. Missing email configuration records `blocked`; configured records are queued. Scheduled Worker execution retries with a stable provider idempotency key, exponential backoff and a bounded attempt count. Administrators can inspect delivery states. Real provider delivery is currently unverified. Resume uploads and analytics are not enabled.

Email configuration is validated before sending. `sent` means provider acceptance, not independently verified inbox delivery. Set `SEND_CONFIRMATIONS=true` only with owner approval: newsletter receipts include private unsubscribe links. Subscription and confirmation writes are atomic; re-subscribing after unsubscribe rotates the private token. Invalid unsubscribe links return an error rather than a false success. Provider failure/retry unit tests use mocks and do not substitute for a credentialed delivery test.
